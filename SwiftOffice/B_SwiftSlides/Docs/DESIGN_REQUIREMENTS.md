# SwiftOffice 设计需求文档

## 核心目标

**用户通过 API 传递两方面关键信息，系统自动完成演示文稿生成**

## 用户传递信息的方式

用户通过以下三种方式向系统传递信息：

1. **协议选择** - 用户通过遵从不同的协议来表达"这是什么类型的页面"
2. **title 文字** - 页面的标题
3. **contents 字典** - 页面的内容数据

## 两方面关键信息

### 1. 文档的整体布局即构成和顺序

通过层级结构和数组顺序决定：

```
Presentation (演示文稿)
  └── Section (PPTX 的 Section)
        └── 章
              └── 节
                    └── 普通页面
```

**说明**：
- `Section` 是 PowerPoint 的专有名词，用于对幻灯片进行分组管理
- "章"和"节"是中文术语，不能翻译成英文的 Section
- 顺序由数组决定

### 2. 单页的具体内容和形式

- **contents 字典**提供内容数据
- **协议**决定呈现形式

## 页面类型

### 结构布局页面

- **示例**：章首页、节首页
- **特点**：用模糊的 key（如 "包含"、"fellowSlides"、"子页面"）
- **目的**：传递层级结构信息
- **协议**：章首页样式、节首页样式
- **关键**：**带页面就不传意念**

### 内容意念页面

- **示例**：具体的内容页面
- **特点**：用精确的 key（如 "普外2科年度目标"、"医疗质量定义"）
- **目的**：传递需要呈现在页面上的内容
- **协议**：ContentStyle、TextStyle、TableSlideStyle 等
- **关键**：**传内容意念就不带页面**

**根本区别**：
- **带页面就不传意念**：结构布局页面通过 `contents` 字典中的 `[any Slide]` 数组传递层级结构，不传递具体内容意念
- **传内容意念就不带页面**：内容意念页面通过 `contents` 字典传递具体内容意念，不传递其他页面

**重要**：一个页面要么是结构布局页面，要么是内容意念页面，不会同时是两者。现实中没有这样的页面。

## 设计理念

### 核心原则

**"内容是一味，呈现看协议"**

### 关键特性

1. **用户可以自由命名字典的 key**
   - key 只是标识符，value 才是信息主体
   - 用户可以用任何他们觉得自然的命名方式

2. **协议决定如何从字典中提取数据**
   - 协议应该智能地从字典中找到匹配的值
   - 不应该硬编码特定的 key

3. **同一个字典可以用不同协议呈现不同效果**
   - 数据和呈现完全分离
   - 用户可以在连续三个页面中使用相同的字典，采用不同的协议，生成不同的幻灯片

## 示例

### 同一个字典，不同协议

```swift
let data: SlideContent = [
    "包含": [
        "医疗质量定义",
        "医疗质量维度"
    ]
]

// 页面1：用 ContentStyle 协议，显示为列表
struct 页面1: Slide, ContentStyle {
    let title = "医疗质量概念"
    let contents = data
}

// 页面2：用 TextStyle 协议，显示为文本
struct 页面2: Slide, TextStyle {
    let title = "医疗质量概念"
    let contents = data

// 页面3：用 节首页样式 协议，显示为导航页
struct 页面3: Slide, 节首页样式 {
    let title = "医疗质量概念"
    let contents = data
}
```

## 协议实现要求

### 协议必须智能地从字典中提取数据

**错误示例**（硬编码 key）：
```swift
public extension 章首页样式 {
    var chapterSlides: [any Slide] {
        contents["fellowSlides"]?.asSlideArray ?? []  // ❌ 硬编码了 key
    }
}
```

**正确示例**（遍历字典）：
```swift
public extension 章首页样式 {
    var chapterSlides: [any Slide] {
        for (_, value) in contents.dict {
            if let slides = value as? [any Slide] {
                return slides
            }
        }
        return []
    }
}
```

### 协议应该根据类型匹配找到正确的值

协议应该遍历字典的所有键值对，找到第一个类型匹配的值，而不是依赖特定的 key 名称。

**结构布局页面**（章首页样式、节首页样式）：
- 找第一个 `[any Slide]` 类型的值

**内容意念页面**（ContentStyle、TextStyle、TableSlideStyle 等）：
- 找第一个匹配的内容类型（如 String、[String]、[[String]] 等）

### 为什么可以这样做

因为一个页面要么是结构布局页面，要么是内容意念页面，不会同时是两者。所以协议可以安全地遍历字典，找到第一个类型匹配的值。

## 层级结构说明

### 层级结构

```
Presentation (演示文稿)
  └── Section (PPTX 的 Section)
        └── 章
              └── 节
                    └── 幻灯片
```

**结构类型**：这是一种树状结构，但不是严格的树状结构。

**特点**：
- 每一个层级都可以直接跳到幻灯片
- 不是严格的父子关系
- 更像是一种灵活的层级结构

**重要**：其中任何一环都可以直接跳到幻灯片，用户可以根据需要选择使用哪些层级。

**灵活的层级使用方式**：

1. **Presentation -> 幻灯片**（最简单）
   - 直接在 Presentation 中定义所有幻灯片
   - 不使用 Section、章、节

2. **Presentation -> Section -> 幻灯片**（中等复杂度）
   - 使用 Section 分组
   - 不使用章、节

3. **Presentation -> Section -> 章 -> 幻灯片**（较复杂）
   - 使用 Section 分组
   - 使用章标识大章节
   - 不使用节

4. **Presentation -> Section -> 章 -> 节 -> 幻灯片**（最复杂）
   - 使用 Section 分组
   - 使用章标识大章节
   - 使用节标识小节

### 为什么需要这么多层级？

#### 1. PowerPoint 的 Section 功能

**Section 是 PowerPoint 的专有功能**：
- PowerPoint 有 Section 功能，用于对幻灯片进行分组
- Section 是 PowerPoint 的专有功能，用户可以在 PowerPoint 中看到和使用
- PPTX 生成需要支持 Section 功能
- 用户可以在 PowerPoint 中通过 Section 来管理和导航幻灯片

#### 2. 逻辑组织

**用户在逻辑上需要分章分节**：
- 章和节是用户在逻辑上组织内容的方式
- 帮助用户更好地管理和理解内容结构
- 例如："第一章 医疗质量概念" -> "1.1 医疗质量定义" -> "1.2 医疗质量维度"

#### 3. 级别首页的必要性

**实际工作中经常需要分级别**：
- 那个级别的首页是需要的
- 他只有一个标题而已，不传递内容意念
- 他的 contents 是一组别的幻灯片
- 但是就是这个标题，也是有颜色字体布局等等差异的

**为什么级别首页是必要的**：
- 级别首页提供了视觉上的分隔和导航
- 帮助听众理解当前的内容结构
- 提供了颜色、字体、布局等视觉差异
- 即使只有一个标题，也是必要的

**为什么不自动添加"第几章第几节"**：
- **因为需要复用，复用的时候，章节都会变**
- 如果系统自动添加"第几章第几节"，那么当用户复用这个幻灯片时，章节号就会不对了
- 应该让用户自己决定是否要写章节号
- 用户可以根据具体情况自由命名

**回归"不带章节号"原则**：
- **用户很聪明，很快就发现他自己不应该写死一个章节号**
- **系统会帮他加，或者根本不用加**
- **否则他想复用就要删掉章节号**
- **还是回归不带章节号原则**

**这其实很基础，跟页码一样**：
- **哪有写死页码的软件？**
- 页码是系统自动生成的
- 用户不需要手动写页码
- 章节号也应该像页码一样，由系统自动生成
- 用户只需要提供内容，系统负责生成页码和章节号

**可以自动添加，但是不能弄死**：
- **在生成的结果上自动添加章节号：这是可以的**
  - 这样不会影响用户在其他地方使用这个幻灯片
  - 这只是显示效果，不影响原始数据
- **不能自动修改用户写的东西**
  - 不能自动修改用户自己写的 title
  - 不能自动修改用户自己写的内容
  - 用户写的东西是原始数据，不能被系统自动修改
- 用户可以选择是否使用自动添加的章节号
- 用户也可以自己手动写章节号
- 这样既提供了便利性，又保持了灵活性

**最佳实践**：
- 用户在定义幻灯片时，**不要写死章节号**
- 例如：`let title = "医疗质量概念"` 而不是 `let title = "第一章 医疗质量概念"`
- 系统在生成的结果上自动添加章节号
- 这样用户可以自由复用幻灯片，不需要手动删除章节号

**示例**：
```swift
struct 章首页_医疗质量概念: Slide, 章首页样式 {
    let title = "第一章 医疗质量概念"  // 用户自己决定是否要写"第一章"
    let contents: SlideContent = [
        "包含": [
            节首页_医疗质量定义(),
            节首页_医疗质量维度()
        ]
    ]
}

// 复用示例
struct 章首页_医疗质量管理: Slide, 章首页样式 {
    let title = "第二章 医疗质量管理"  // 复用时，章节号可以自由修改
    let contents: SlideContent = [
        "包含": [
            节首页_质量管理工具(),
            节首页_质量管理方法()
        ]
    ]
}
```

这个章首页：
- 只有一个标题："第一章 医疗质量概念"（用户自己决定是否要写"第一章"）
- 不传递内容意念
- contents 是一组别的幻灯片（节首页）
- 但是这个标题有颜色、字体、布局等视觉差异
- 提供了视觉上的分隔和导航
- 复用时，章节号可以自由修改

#### 4. 灵活性和可扩展性

**多层级设计提供了极大的灵活性**：
- 用户可以根据具体需求选择使用哪些层级
- 不需要强制使用所有层级
- 可以根据项目的复杂度选择合适的层级

#### 4. 复用性

**每个层级都可以独立定义和复用**：
- 同一个 `[any Slide]` 数组可以在不同层级使用
- 同一个幻灯片可以在多个地方引用
- 便于维护和修改

#### 5. 清晰的结构

**多层级设计使文档结构更加清晰**：
- 便于理解和导航复杂内容
- 提高了整体的可读性和可用性
- 累加起来就是整个布局

### Presentation (演示文稿)

**作用**：整个 PPTX 文件的根节点

**定义方式**：
```swift
struct 我的演示文稿: Presentation {
    let title = "医疗质量与安全管理"
    let sections: [any Section] = [
        第一章(),
        第二章(),
        第三章()
    ]
}
```

**说明**：
- `sections` 是一个 `[any Section]` 类型的数组
- 决定了整个 PPTX 的 Section 数量和顺序
- 可以省略，直接在 Presentation 中定义所有幻灯片

### Section (PPTX 的 Section)

**作用**：PowerPoint 中的分组管理单位

**定义方式**：
```swift
struct 第一章: Section {
    let title = "第一章 医疗质量概念"
    let slides: [any Slide] = [
        章首页_医疗质量概念(),
        节首页_医疗质量定义(),
        医疗质量定义页(),
        节首页_医疗质量维度(),
        医疗质量维度页()
    ]
}
```

**说明**：
- `slides` 是一个 `[any Slide]` 类型的数组
- 决定了该 Section 内的页面数量和顺序
- 这个数组的元素会直接出现在最终的 PPTX 中
- 可以省略，直接在 Section 中定义章首页或节首页

### 章

**作用**：逻辑上的大章节，通过章首页标识

**定义方式**：
```swift
struct 章首页_医疗质量概念: Slide, 章首页样式 {
    let title = "第一章 医疗质量概念"
    let contents: SlideContent = [
        "包含": [  // 或 "fellowSlides", "子页面" 等任何用户喜欢的 key
            节首页_医疗质量定义(),
            节首页_医疗质量维度()
        ]
    ]
}
```

**说明**：
- 章首页本身是 `Section.slides` 数组中的一个元素
- 章首页通过 `contents` 字典中的 `[any Slide]` 类型的值定义包含的节首页
- 章首页的 `contents` 字典中的 `[any Slide]` 数组不会直接出现在最终的 PPTX 中，它只是用于逻辑组织
- 可以省略，直接在 Section 中定义节首页或普通页面

### 节

**作用**：逻辑上的小节，通过节首页标识

**定义方式**：
```swift
struct 节首页_医疗质量定义: Slide, 节首页样式 {
    let title = "1.1 医疗质量定义"
    let contents: SlideContent = [
        "包含": [  // 或 "fellowSlides", "子页面" 等任何用户喜欢的 key
            医疗质量定义页(),
            医疗质量案例页()
        ]
    ]
}
```

**说明**：
- 节首页本身是 `Section.slides` 数组中的一个元素
- 节首页通过 `contents` 字典中的 `[any Slide]` 类型的值定义包含的具体页面
- 节首页的 `contents` 字典中的 `[any Slide]` 数组不会直接出现在最终的 PPTX 中，它只是用于逻辑组织
- 可以省略，直接在 Section 中定义普通页面

### 幻灯片

**作用**：具体的内容页面

**定义方式**：
```swift
struct 医疗质量定义页: Slide, ContentStyle {
    let title = "医疗质量定义"
    let contents: SlideContent = [
        "包含": [  // 或任何用户喜欢的 key
            "医疗质量是指医疗卫生服务在现有医学知识和技术条件下",
            "达到的合理程度，满足患者及社会期望的程度"
        ]
    ]
}
```

**说明**：
- 普通页面是 `Section.slides` 数组中的一个元素
- 普通页面通过 `contents` 字典提供具体内容数据
- 普通页面遵循各种内容样式协议（如 `ContentStyle`、`TextStyle`、`TableSlideStyle` 等）

## 用户如何定义 PPTX 的页面数量和顺序

**关键**：用户在哪里提供 `[any Slide]` 数组，决定了最终的 PPTX 结构。

### 方式 1：Presentation -> 幻灯片（最简单）

```swift
struct 我的演示文稿: Presentation {
    let sections: [any Section] = [
        Section(title: "所有幻灯片", slides: [
            幻灯片1(),  // 页面 1
            幻灯片2(),  // 页面 2
            幻灯片3()   // 页面 3
        ])
    ]
}
```

**说明**：
- 直接在 Section 中定义所有幻灯片
- 不使用章首页和节首页
- 最简单的方式

### 方式 2：Presentation -> Section -> 幻灯片（中等复杂度）

```swift
struct 我的演示文稿: Presentation {
    let sections: [any Section] = [
        Section(title: "第一章", slides: [
            幻灯片1(),  // 页面 1
            幻灯片2()   // 页面 2
        ]),
        Section(title: "第二章", slides: [
            幻灯片3(),  // 页面 3
            幻灯片4()   // 页面 4
        ])
    ]
}
```

**说明**：
- 使用 Section 分组
- 不使用章首页和节首页
- 适合中等复杂度的 PPTX

### 方式 3：Presentation -> Section -> 章 -> 幻灯片（较复杂）


### 方式 4：Presentation -> Section -> 章 -> 节 -> 幻灯片（最复杂）

```swift
struct 我的演示文稿: Presentation {
```

- 章首页和节首页的 `contents` 字典只是用于告诉系统逻辑关系，不影响最终 PPTX 的顺序

## 总结

**用户定义 PPTX 的方式**：

1. **页面数量**：由所有层级中的 `[any Slide]` 数组累加决定
2. **页面顺序**：由所有层级中的 `[any Slide]` 数组累加顺序决定
3. **分章分节**：
   - 章通过章首页标识
   - 节通过节首页标识
   - 章和节的关系通过章首页和节首页的 `contents` 字典中的 `[any Slide]` 数组表达
4. **[slides] 出现的地方**：
   - `Presentation.sections`：提供 `[any Section]` 数组
   - `Section.slides`：提供 `[any Slide]` 数组
   - `章首页样式.章幻灯片`：提供 `[any Slide]` 数组
   - `节首页样式.节幻灯片`：提供 `[any Slide]` 数组

**关键点**：

1. **Presentation 只知道有多少个 `[any Slide]`，不知道他们自身又"带上"多少个下级**
   - 每一个级别都一样的
   - 最终级别都没有"带上的"页面了，所以不会有问题

2. **只要有带页面的，所带的是什么，就必须通过询问所带的那个东西，才知道他是遵从什么协议的**
   - 内容是给定的
   - 协议是可变的
   - **这样做，才能给用户最大的复用灵活性**

3. **累加起来就是整个布局**
   - 用户在不同层级提供 `[any Slide]` 数组
   - 这些数组累加起来就形成了整个 PPTX 的布局

**设计优势**：

1. **用户写起来非常自然**
   - 用户可以在任何层级提供 `[any Slide]` 数组
   - 不需要强制使用所有层级
   - 可以根据需要选择使用哪些层级

2. **用起来非常方便**
   - 可以有基本部件放着不用
   - 可以复用于不同的场合
   - 灵活组合，适应不同的需求

3. **可复用性强**
   - 同一个 `[any Slide]` 数组可以在不同层级使用
   - 同一个幻灯片可以在多个地方引用
   - 便于维护和修改

**有了完整信息，我们可以做很多事情**：

当我们通过自然简洁的API，拥有了以上用户提供的全部信息之后，我们可以做很多很多东西：

1. **自动生成目录**
   - 因为我们有了完整的层级结构信息（Presentation -> Section -> 章 -> 节 -> 幻灯片）
   - 可以自动生成目录
   - 可以自动更新目录

2. **在任何页面提供完整导航**
   - 因为我们有了所有幻灯片的信息
   - 可以在任何页面提供完整导航
   - 可以提供跳转到任何页面的链接

3. **提供面包屑导航**
   - 可以显示当前页面的层级路径
   - 例如：第一章 > 1.1 医疗质量定义

4. **提供上一页/下一页导航**
   - 可以提供上一页/下一页按钮
   - 可以提供跳转到首页/末页按钮

5. **提供章节导航**
   - 可以提供跳转到上一章/下一章按钮
   - 可以提供跳转到上一节/下一节按钮

**系统灵活性**：

用户在普通页面上：
1. **提供了数据（data）**
2. **选择了协议（决定呈现方式）**

接下来：
- **根据协议的特点，怎么摆放美观，就是系统的事情了**

**示例**：

```swift
// 用户提供了数据
let data = [
    "普外2科年度目标": [
        "提高医疗质量",
        "降低医疗成本",
        "提升患者满意度"
    ]
]

// 用户选择了协议（ContentStyle）
struct 年度目标页: Slide, ContentStyle {
    let title = "年度目标"
    let contents: SlideContent = data
}

// 系统根据 ContentStyle 协议的特点，决定怎么摆放美观
// - 列表项应该用什么字体
// - 列表项应该用什么颜色
// - 列表项应该用什么间距
// - 列表项应该用什么对齐方式
// - 等等...
```

**关键点**：
- 用户只需要提供数据和选择协议
- 系统负责根据协议的特点，决定怎么摆放美观
- 这样用户不需要关心具体的布局细节
- 系统可以根据协议的特点，自动优化布局

**优势**：
- 用户可以专注于内容
- 系统可以保证美观
- 系统可以根据协议的特点，自动优化布局
- 用户不需要关心具体的布局细节

## 总结

**设计需求异常简单**：用户通过协议选择 + title 文字 + contents 字典，向我们传递文档的整体布局即构成和顺序，以及单页的具体内容和形式。这两方面就是我们完成生产的全部所需信息。

**关键点**：
- contents 是一个字典，key 是用户自由命名的，value 才是信息主体
- 协议决定呈现方式，字典只是数据容器
- 用户可以在连续三个页面中使用相同的字典，采用不同的协议，生成不同的幻灯片
